# Discovery Engine v2 — "which stocks does the engine look at?"

**Date:** 2026-09-22 · **Status:** design, being built on branch `engine/discovery-v2` (worktree from 74ad5f7 = deployed main)
**Extends** `2026-08-11-funnel-and-regret-learning-design.md` §4.1 (Seeing). Scoring, calibration, grading, lanes, regret loop: unchanged.

## 1. Problem

The funnel's first stage — *seeing* — is a sampled view of the market, not the market:

- Discovery inflow = three Yahoo predefined screens (`day_gainers` 50, `day_losers` 25, `most_actives` 25) + a hand-curated core sleeve (~130 names ranked by one 3-month spark batch of closes only) + an 80-name roster that only admits names that already "showed they can travel" (`JOIN_CAPACITY = 8`) and trims the largest caps first.
- Everything that is not a top-50 mover *today* or a sleeve member is invisible: steady relative-strength runners, quiet breakouts, pullbacks-in-uptrend on large names, sector rotations, UK mid caps, and anything that moved yesterday but not today.
- Screens are US-only, unstable (Yahoo re-ranks intraday; a run at 07:58 UTC sees a different list than one at 05:35), fail to `[]`, and carry no memory.
- Market cap for cohorts depends on Finnhub `profile2`, which refuses ~78% of calls at the account level.

The owner's verdict (2026-08-11) still stands: easy wins "came and went" unseen. The 2026-08 funnel work fixed *what the engine does with what it sees*; this project fixes *what it sees*.

Conclusion: a ~2,000-name daily full-universe OHLCV scan costs ~30 s and $0. There is no reason to sample.

## 3. Design principles

1. **Universe first, screens last.** The engine scans a persistent, explicit universe every run. Yahoo screens, social, news and LLM catalysts become *nominators* that can add names to the universe (and raise priority), never the sole way to be seen.
2. **Cross-sectional, not absolute.** Every feature is ranked as a percentile across the universe that day. "Unusual" means unusual *relative to the market and to the name's own history*, so the lens works in calm and wild tapes alike.
3. **Many lenses, one ledger.** Each lens is a pure function candles → score with a stated hypothesis. Names are selected per lens (top-N with sector diversification), tagged with the lens that found them, so the existing calibration/setup-family machinery can learn which lenses are worth anything.
4. **Deterministic and explainable.** Same inputs → same candidate list; every universe name gets a one-line discovery trace (found by / ranked / rejected because).
5. **Fail-soft, budgeted, incremental.** Per-name fetch failures never kill the run; a hard time/request budget caps the scan; bars are cached incrementally in the store so a warm run fetches only the missing tail.
6. **Nothing downstream changes.** Discovery emits candidates into the existing pool with `source` tags; composeCall, calibration, grades, risk ladder, lanes and the regret loop are untouched. Old sources stay as fallback when the scan fails.

## 4. Components (`shared/engine/discovery/`, pure; I/O in `netlify/functions/lib/discovery*.ts`)

### 4.1 Universe (`universe.ts`, seed in `universe.seed.json`)
- **Seed**: S&P 500 + Nasdaq-100 + S&P 400 + S&P 600 + FTSE 100 + FTSE 250, Yahoo-validated, with `capBand` from index membership (no Finnhub dependency). Regenerated by `scripts/build-universe-seed.ts`; committed.
- **Dynamic members** (`universe:v1` blob): names nominated by screens, social/hype clusters, LLM catalysts, news, watchlist, holdings, and the legacy core sleeve join with `joinedAt`, `lastSeenBy`, and expire after 60 sessions unless re-nominated or selected. Hard cap 600 dynamic names.
- **Hygiene** (applied at scan): ETP guard (`isRouteEtp`), price ≥ $2 (or ≥ 50p), 20-day median dollar volume ≥ $5M (US) / £2M (UK), ≥ 60 bars of history, no bar older than 3 sessions (stale/delisted), crypto excluded (own lane).

### 4.2 Bars (`netlify/functions/lib/discoveryBars.ts`)
- Fetch daily OHLCV via `fetchYahooChart` (existing parser) at concurrency 8 with retry-on-429 backoff, under a wall-clock budget (default 120 s) and a per-run request cap.
- Incremental cache in the store: `dbars:{sym}` = compact `{ t:number[], o,h,l,c,v:number[] }` (last 300 bars). Warm run: request `range=1mo` and splice; cold: `range=1y`. Per-symbol failure → serve cached if fresh enough (≤ 3 sessions), else skip with trace `no-bars`.
- Stooq fallback only for names with no cache at all.

### 4.3 Features (`features.ts`, pure)
Per name from ≥ 60 bars: returns 1/5/10/20/60d, gap%, ATR14%, `typicalMove10` (existing swingCapacity), RVOL (today vol / 20d median), dollar volume, EMA8/21/50 stack + distance, RSI14, drawdown from 20d/60d high, distance to 52w high, up-days of last 5/10, 20d high/low breaks, Bollinger-width percentile over 120d (compression), relative strength vs SPY 20/60d, 5d volume trend.

### 4.4 Lenses (`lenses.ts`, pure; each returns a 0–1 score + reason or null)
| lens | hypothesis | family it feeds |
|---|---|---|
| `unusual` | today's move ÷ own typical move is extreme (both signs) | continuation / fade (existing dead-zone math decides) |
| `rs-leader` | top-decile RS vs SPY over 20 and 60d, above rising EMA50, not extended (< 2 ATR above EMA21) | continuation — the "steady runner" |
| `pullback` | RS leader pulled back to EMA21 (±1 ATR) on falling volume, no EMA50 loss | continuation (reversal-in-trend) |
| `breakout` | close above 20d/60d high on RVOL ≥ 2, from a compressed base (BB-width pctl ≤ 30) | velocity early door |
| `dip` | drawdown ≥ 12% from 20d high or gap ≤ −7%, large/core name, hold evidence (reclaim trigger low or EMA50 on RVOL ≥ 1.5) | dip lane (existing constructor) |
| `weak` | bottom-decile RS, below falling EMA50, lower highs; routable-short candidates | continuation short |
| `climax` | ≥ 5 up-days of 6, extension ≥ 3 ATR above EMA21, RVOL fading | fade short / velocity-avoid flag |

### 4.5 Ranking + selection (`rank.ts`, pure)
- Percentile-rank each raw feature across the day's universe; lens scores are built from percentiles so thresholds are tape-relative.
- Per lens: top-N (N per lens, defaults sum ≈ 120) with a sector cap (≤ 30% of a lens's picks from one sector) and a per-name cap of 2 lenses (best two kept).
- Priority weights: names nominated by ≥ 2 independent nominators (news + social + lens, etc.) get a bump; watchlist/holdings always pass hygiene-only.
- Output: `DiscoveryCandidate { sym, lenses:[{lens, score, reason}], features, capBand, exchange, priority }` + `DiscoveryTrace` rows for every universe name (found-by / rejected-by code).

### 4.6 Wiring (`engine.ts` `buildBoard`)
- New source family `scan:<lens>` added to the candidate pool ahead of screens; `capUsdM` filled from cache when present else cohort from `capBand`.
- Candidate budget rises to accommodate ~120 scan picks; screens/sleeve/roster keep feeding (they mostly overlap now) and remain the fallback when `runDiscovery` throws or returns < 20 names (`DISCOVERY=off` env kills the stage entirely, legacy path unchanged).
- Discovery trace persisted as `discovery-trace:{date}` (bounded) beside the funnel trace so "why wasn't X seen?" is answerable.

## 5. Testing
- Pure modules: synthetic-candle fixtures per lens (positive, negative, edge), percentile ranking determinism, sector cap, hygiene rules, seed loader.
- Bars layer: mocked fetch — 429 backoff, budget cut, incremental splice correctness, stale-cache serving.
- Engine wiring: candidate pool contains `scan:*` sources; `DISCOVERY=off` byte-identical to today; discovery failure falls back cleanly.
- Live: `scripts/discovery-dry-run.ts` runs the real scan and prints timing, counts per lens, top names — the ship gate is a clean run under 3 minutes with ≥ 90% bars coverage.

## 6. Out of scope
Changing composeCall, calibration keys, hit definition, grades, risk ladder, lanes' internal rules; paid data; intraday scanning; options/futures.
