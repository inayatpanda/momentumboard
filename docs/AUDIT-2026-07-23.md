# The Street Signal / momentumboard — production security and reliability audit

**Audit date:** 23 July 2026 (Europe/London)  
**Repository reviewed:** `d4834473a80653ea9db90ec7ba624f75657c347b`  
**Production targets:** `https://thestreetsignal.rqai.co.uk` and `https://thestreetsignal.netlify.app`  
**Posture:** read-only. No production writes, report composition, webhook POSTs, licence mint/revoke, queue draining, or scheduled scripts were run.

## Executive summary

1. **High — one bearer secret is reused for four incompatible trust boundaries.** `REPORT_TOKEN` authenticates Telegram webhook deliveries, grants the Helm export of the owner's private history/config/trades, and can publish a report (which triggers real email/push/Telegram delivery). A Telegram webhook secret is therefore also a production-publish and private-export credential. This is a confirmed design flaw, even though the public webhook correctly rejected the unauthenticated GET probe.

2. **High — the daily worker can report success after failing to publish.** The composer records `putHtml.ok` and `putPicks.ok` but always returns `200 ok`; the GitHub Action only fails on a `>=400` composer response. A rejected/misrouted report PUT or failed structured-picks PUT can therefore leave Actions green and readers without a paper or without accountability data. This is confirmed by code path, not exercised live.

3. **High — the LLM router destroys the useful cause of provider failures.** A mocked Groq HTTP 429 was locally reproduced as `groq-empty`. Each provider parses JSON but never checks `res.ok`, so actual quota/auth/model errors are replaced with an “empty response” symptom. This directly explains why the reported 23 July `groq-empty` incident was hard to diagnose.

4. **Medium — the production archive has missing daily editions, including weekdays.** At 18:13–18:17 GMT, `/report?list=1` listed 2–3 and 7–8 July, then 10–23 July, with no editions for 4–6 or 9 July. The code promises weekend/holiday editions as well as weekday publication. This is confirmed historical availability evidence; read-only access cannot establish the incident cause.

5. **Medium — the PWA is not offline-navigable at its configured start URL.** The service worker precaches `index.html`, but neither `/app/` nor `/app/index.html`, and has no navigation fallback. Workbox will look for `/app/index.html` when an offline installed PWA opens `/app/`; it will miss. The worker also registers at `/` despite the manifest scope being `/app/`.

6. **Medium — baseline browser hardening is absent.** The deployed root, JS/CSS, manifest, and report responses lack a CSP, frame-ancestors/X-Frame-Options, Referrer-Policy, Permissions-Policy and cross-origin isolation policy. The current paper itself escapes LLM strings correctly, so I found **no confirmed LLM HTML/XSS execution path**; the missing policy is defence-in-depth and makes any future escaping regression substantially worse. It also leaves authenticated UI clickjacking unmitigated.

7. **Medium — the edition makes a verified false political statement and presents unsourced market claims as fact.** The live 23 July paper calls Donald Trump “former President”; the White House identifies him as the 45th and 47th President. The rest of the same lead makes consequential geopolitical claims with no reader-visible source/citation. This undermines editorial reliability in an app positioning itself as a daily research paper.

8. **The core access checks generally held up in safe live probes.** Unauthenticated `/api/engine`, `/api/market`, `/api/export`, `/api/config`, `/api/licences`, and the direct Telegram webhook all rejected requests. Licence keys have 144 random bits after the `mb_` prefix; I found no practical anonymous enumeration endpoint. The LLM newspaper renderer consistently HTML-escapes prose and table fields.

## Methodology and limits

### Production checks performed

I made a single, small GET/OPTIONS/HEAD-style probe per listed route (plus one invalid licence token check), using `/usr/bin/curl` with a 30-second maximum. I checked response status, body shape/size, selected headers, deployed manifest/worker assets, source-map fall-through, and the certificate. I fetched no authenticated data because no credential was supplied and I did not search for one.

I also attempted the provided in-app browser control surface for visual/PWA validation. It reported **“No browser is available”** in this environment, so mobile rendering, installed-app registration, and actual offline navigation were assessed from deployed assets and source rather than an interactive browser.

The live edition was read at `/report` and compared with current official government/White House pages where a claim needed verification. The report itself is public; no data was modified.

### Code and build checks performed

- Read the route declarations, all relevant public handlers, auth/licensing, report compose/publish path, LLM router, service worker, selected fetchers, the prediction/calibration/risk ladder, the 23 July freshness commit, and the two GitHub Actions workflows.
- Searched all function/script `fetch(` calls and queue writers for user-controlled URL/SSRF paths.
- Ran `npm test`: **91 test files / 690 tests passed**.
- Ran `npm run build`: TypeScript and Vite build succeeded. Vite emitted a 770.83 kB uncompressed / 242.34 kB gzip initial JS chunk warning.
- Locally mocked one Groq 429 response without calling any provider. The router threw `groq-empty`, as described in Finding H-3.

### Out of scope by safety constraint

I did **not** PUT/POST `/report`, POST the Telegram webhook, create/revoke trials or licences, call Action scripts against production, write blobs, send email, invoke Telegram, or load-test/race production. Claims about those paths are explicitly marked code-confirmed or theoretical.

## Findings

### High

#### H-1 — `REPORT_TOKEN` is a webhook secret, private export credential, and production publisher key

**Status:** Confirmed by source; live unauthenticated webhook gate confirmed.

**Evidence / reproduction**

- Telegram accepts a request when `x-telegram-bot-api-secret-token === REPORT_TOKEN`: [telegram-webhook.mts](/Users/inayat/Projects/momentumboard/netlify/functions/telegram-webhook.mts:19). The live safe `GET /.netlify/functions/telegram-webhook` returned `401 unauthorized`, demonstrating the gate is deployed.
- The same header value authorizes the report publisher: [report.mts](/Users/inayat/Projects/momentumboard/netlify/functions/report.mts:71). A successful HTML PUT writes the public edition and may notify Telegram, email recipients and push subscribers at [report.mts](/Users/inayat/Projects/momentumboard/netlify/functions/report.mts:131), [report.mts](/Users/inayat/Projects/momentumboard/netlify/functions/report.mts:146), and [report.mts](/Users/inayat/Projects/momentumboard/netlify/functions/report.mts:167).
- The same token authorizes Helm export: [helm-export.mts](/Users/inayat/Projects/momentumboard/netlify/functions/helm-export.mts:49). That export includes archived HTML, picks, private journal trades, notes and config at [helm-export.mts](/Users/inayat/Projects/momentumboard/netlify/functions/helm-export.mts:84) and [helm-export.mts](/Users/inayat/Projects/momentumboard/netlify/functions/helm-export.mts:98).
- GitHub Actions also inject this shared secret into both workers: [daily-paper.yml](/Users/inayat/Projects/momentumboard/.github/workflows/daily-paper.yml:32) and [queue-worker.yml](/Users/inayat/Projects/momentumboard/.github/workflows/queue-worker.yml:30).

**Impact**

A secret necessarily provisioned to the Telegram webhook integration is also a bearer capability to overwrite the live report and to extract owner data. Any leak via a webhook configuration, proxy/header log, Actions secret exposure, developer machine, or mistaken reuse crosses all three boundaries. Publishing is especially damaging because it sends genuine outbound communications and changes a real user-facing edition.

**Recommended fix**

Create distinct, high-entropy secrets with narrow scopes: `TELEGRAM_WEBHOOK_SECRET`, `REPORT_PUBLISH_TOKEN`, and `HELM_EXPORT_TOKEN`. Prefer Netlify/Actions-to-function service authentication or a signed, short-lived internal assertion for publish calls. Rotate the current `REPORT_TOKEN` after separation, remove it from Telegram webhook registration, and add a regression test that each token is rejected by the other routes.

#### H-2 — Compose/publish failures are recorded then converted into success

**Status:** Confirmed by source; deliberately not reproduced against production.

**Evidence / reproduction**

The composer sends two state-changing PUTs, then merely logs both outcomes:

- HTML PUT: [report-compose-background.mts](/Users/inayat/Projects/momentumboard/netlify/functions/report-compose-background.mts:480)
- picks PUT: [report-compose-background.mts](/Users/inayat/Projects/momentumboard/netlify/functions/report-compose-background.mts:491)
- log-only handling: [report-compose-background.mts](/Users/inayat/Projects/momentumboard/netlify/functions/report-compose-background.mts:499)
- unconditional `ok` return: [report-compose-background.mts](/Users/inayat/Projects/momentumboard/netlify/functions/report-compose-background.mts:522)

The Actions entry point treats the run as failed only when the composer response is `>=400`: [daily-run.mts](/Users/inayat/Projects/momentumboard/scripts/bg/daily-run.mts:54)–[daily-run.mts](/Users/inayat/Projects/momentumboard/scripts/bg/daily-run.mts:58). Therefore a `401`, `500`, or network response returned by `/report` can be logged as `htmlOk: false` while the handler returns `200`, and the Action reports success. A failed picks PUT is even less visible: the paper can be live while its scorecard/ledger source is absent.

**Impact**

The owner can see a green scheduled run while no new edition exists, or readers can receive an edition whose picks were never recorded. The watchdog may catch the missing paper later, but it cannot recover missing picks and is not the Action's primary success criterion.

**Recommended fix**

Require `putHtml.ok`; return a non-2xx response with a sanitized status/body diagnostic when it fails. Treat picks as transactional enough to retry and alert: either publish picks before HTML, use an idempotent single publish endpoint/envelope, or return a distinct failure and enqueue a retry. Write the success runlog/history only after both required writes succeed. Add tests for HTML 401/500 and picks 500 asserting Action-visible failure.

#### H-3 — Provider HTTP failures are misleadingly reported as `groq-empty`

**Status:** Confirmed by source and local deterministic reproduction; no provider request was sent.

**Evidence / reproduction**

Each provider parses a JSON response and only then checks for generated text; it never rejects `!res.ok`. For Groq, [llm.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/llm.ts:60)–[llm.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/llm.ts:68) turns any error JSON without `choices[0].message.content` into `Error('groq-empty')`. Gemini, OpenAI, and Anthropic repeat the pattern at [llm.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/llm.ts:75), [llm.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/llm.ts:92), and [llm.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/llm.ts:108).

Local no-network reproduction:

```text
npx tsx -e "... callLlm(... mocked Response(..., {status: 429})) ..."
mock HTTP 429 error becomes: groq-empty
```

The router does fall through to another configured provider at [llm.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/llm.ts:127)–[llm.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/llm.ts:140), but if the fallback is absent, exhausted, invalid, or also fails, the only surfaced cause is the last generic `*-empty` error. This code path is consistent with the reported `groq-empty` daily-paper incident; I did not have permission to inspect GitHub Actions logs to attribute that specific incident beyond the user's report.

**Impact**

An expired key, invalid/retired model, quota limit, provider outage, content rejection, or malformed upstream payload is operationally indistinguishable from an empty completion. That delays incident response and makes automated alerting inaccurate.

**Recommended fix**

Check `res.ok` first. Parse error bodies defensively, preserve provider/status/error-code in a bounded error such as `groq HTTP 429: rate_limit_exceeded`, and classify retryable vs permanent failures. Return structured provider diagnostics to the runlog without secrets. Test 401, 429, 404-model, 5xx and invalid JSON for every provider.

#### M-2 — Winter daylight-saving drift publishes an hour earlier than the stated UK schedule

**Status:** Confirmed by static schedule/time-zone analysis.

**Evidence**

The new daily workflow runs at fixed `05:35 UTC`: [daily-paper.yml](/Users/inayat/Projects/momentumboard/.github/workflows/daily-paper.yml:9)–[daily-paper.yml](/Users/inayat/Projects/momentumboard/.github/workflows/daily-paper.yml:10). **Status:** Confirmed from deployed worker and source; interactive offline test unavailable because no browser was available.

**Evidence**

The PWA manifest uses `start_url` and `scope` `/app/`: [vite.config.ts](/Users/inayat/Projects/momentumboard/vite.config.ts:15)–[vite.config.ts](/Users/inayat/Projects/momentumboard/vite.config.ts:19). #### M-4 — Security headers leave the authenticated app frameable and lack CSP containment

**Status:** Confirmed live configuration gap; no XSS execution found.

**Evidence**

Live root response headers were:

```text
GET / → 200
Cache-Control: public,max-age=0,must-revalidate
Strict-Transport-Security: max-age=31536000
```

Live report added only `X-Content-Type-Options: nosniff`; the root, report, JS, CSS and manifest had no `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy`, `Permissions-Policy`, or CORS allow-origin header. The missing header configuration is reflected in [netlify.toml](/Users/inayat/Projects/momentumboard/netlify.toml:1), which defines redirects but no headers.

This is not a claim that current newspaper output is executable. The renderer escapes LLM text (`&`, `<`, `>`, quotes) at [newspaper.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/newspaper.ts:576)–[newspaper.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/newspaper.ts:584), and all key LLM fields are passed through it, for example [newspaper.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/newspaper.ts:806)–[newspaper.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/newspaper.ts:826) and [newspaper.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/newspaper.ts:648)–[newspaper.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/newspaper.ts:652). The live paper contained no script tags or non-canonical links in its rendered editorial content.

**Impact**

The `x-app-token` is kept in localStorage, so a future DOM XSS is an account/data compromise. Without CSP, a single escaping regression or dependency compromise has a much larger blast radius. Without frame protection, a hostile page can iframe the UI and attempt clickjacking against authenticated user actions. The header gap also contributes to query-token referrer/log exposure risk below.

**Recommended fix**

Add Netlify headers for all HTML: a strict nonce/hash-based CSP (start in report-only mode if necessary), `frame-ancestors 'none'` (or `X-Frame-Options: DENY`), `Referrer-Policy: no-referrer`, a minimal Permissions-Policy, and `X-Content-Type-Options: nosniff`. Test the report, PWA, Google Fonts, and service-worker flows before enforcing. Keep the existing renderer escaping and add hostile `<img onerror>`, `<svg>`, `javascript:` and entity payload tests around every template field.

**Status:** Confirmed live editorial error.

**Evidence**

#### M-6 — Query-string licence links expose long-lived bearer credentials to URL handling

**Status:** Confirmed design risk; no credential was used or exposed during this audit.

**Evidence**

Unlock URLs are constructed as `/?key=<licence>` at [licences.mts](/Users/inayat/Projects/momentumboard/netlify/functions/licences.mts:84)–[licences.mts](/Users/inayat/Projects/momentumboard/netlify/functions/licences.mts:94). The client stores the key in localStorage and removes it from browser history only after the initial request has arrived: [main.tsx](/Users/inayat/Projects/momentumboard/src/main.tsx:9)–[main.tsx](/Users/inayat/Projects/momentumboard/src/main.tsx:20). The deployed site has no Referrer-Policy (M-4).

**Impact**

The original URL can enter CDN/access logs, browser history/sync, support screenshots, copied links, and same-origin asset request referrers before `replaceState` executes. Because licences are bearer credentials, anyone obtaining the full link can use the reader's account namespace until revoked/expired.

**Recommended fix**

Use a single-use, short-lived redemption code in the URL; exchange it for a licence through a POST and invalidate it immediately. Do not put perpetual bearer keys in links. Add `Referrer-Policy: no-referrer`, use URL fragments only where compatible with the exchange flow, and provide a visible “remove/rotate this device key” control.

#### M-7 — Trial rate limiting is a non-atomic blob read-modify-write and can be raced

**Status:** Code-confirmed concurrency weakness; not attempted against production.

**Evidence**

The public trial route reads `trial-issues`, checks limits, mints a licence, then writes the updated array at [licences.mts](/Users/inayat/Projects/momentumboard/netlify/functions/licences.mts:57)–[licences.mts](/Users/inayat/Projects/momentumboard/netlify/functions/licences.mts:75). There is no lease, conditional write, durable rate-limiter, or post-write verification for `trial-issues`. The application itself documents eventual-consistency hazards in Blobs and only mitigates licence-list writes with strong rereads at [auth.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/auth.ts:59)–[auth.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/auth.ts:74); that mitigation does not make the rate-limit counter atomic.

**Impact**

Concurrent requests can all observe a quota below the per-IP/global limit, each mint a valid seven-day licence, then overwrite each other's issue record. This allows more trial keys than the stated 2/IP/week and 25/day circuit breaker, creating abuse and LLM/API cost exposure. It is not a licence-key guessing attack: generated keys are 18 random bytes ([auth.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/auth.ts:49)–[auth.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/auth.ts:51)).

**Recommended fix**

Move rate limiting to an atomic provider (Netlify Edge rate limiting, Redis/KV atomic increment, or a durable database transaction) keyed on a privacy-preserving salted IP/device key. Ensure the trial issuance itself is idempotent and return an existing active trial rather than minting another key. Alert on rate-limit anomalies.

### Low

#### L-1 — Static assets are hash-named but forced to revalidate; initial mobile JS is large

**Status:** Confirmed live/build performance issue.

**Evidence**

The deployed initial JS is 771,706 bytes and CSS 67,950 bytes; both return `Cache-Control: public,max-age=0,must-revalidate` despite content-hashed names. The build reproduced Vite's warning: the initial JS is 770.83 kB (242.34 kB gzip), above the 500 kB warning threshold. The service worker precaches roughly 924 KiB, which helps repeat visits only after installation and successful worker activation.

**Impact**

Cold mobile startup depends on a large single bundle and every normal visit revalidates hash-stable assets. On poor UK mobile connections this conflicts with the PWA/fast-desk intent.

**Recommended fix**

Set immutable, long-lived cache headers for `/assets/*` content-hashed files; keep HTML/manifest/worker short-cache/no-cache. Split charting, PDF, desk/quant, and rarely visited screens with dynamic imports. Track real mobile LCP/INP and bundle size in CI.

#### L-2 — Manifest is served as `application/octet-stream`

**Status:** Confirmed live; browser install compatibility not interactively tested.

**Evidence**

`GET /manifest.webmanifest` returned `200` with `Content-Type: application/octet-stream`, not `application/manifest+json` or `application/json`. It contains valid JSON and the intended `/app/` start/scope fields.

**Impact**

Some browsers are permissive, but this is needlessly dependent on MIME sniffing and can produce install/diagnostic inconsistencies, especially once `nosniff` is correctly applied globally.

**Recommended fix**

Set an explicit `Content-Type: application/manifest+json; charset=utf-8` for `manifest.webmanifest` in Netlify headers and verify installability in Chrome and Safari/iOS where supported.

#### L-3 — Freshness pass is fail-open and may reintroduce unvalidated prose

**Status:** Code-confirmed design limitation; no live repeat was found/forced.

**Evidence**

The new `d483447` helper correctly detects normalized, >=45-character verbatim sentence repeats: [newspaper.ts](/Users/inayat/Projects/momentumboard/netlify/functions/lib/newspaper.ts:271). The composer then gives a model the full affected sections and accepts replacement text based only on type and relative length: [report-compose-background.mts](/Users/inayat/Projects/momentumboard/netlify/functions/report-compose-background.mts:420)–[report-compose-background.mts](/Users/inayat/Projects/momentumboard/netlify/functions/report-compose-background.mts:458). It runs **after** the limited front-page claims audit and does not rerun it.

**Impact**

The repetition feature improves prose freshness but can silently alter numbers, scope, or factual assertions in `tape`, `shortDesk`, `rotation`, etc. Its errors are deliberately swallowed, so both a failed freshness pass and a dangerous rewrite are operationally hard to distinguish.

**Recommended fix**

Restrict the rewrite to the specific repeated sentences, retain a before/after diff in the runlog, and validate all numeric tokens/tickers against the original/data before applying. Rerun the claims validation after rewriting. Add an integration test with a malicious/incorrect rewrite response, not only helper-unit tests.

## Security and product checks that passed or were not findings
